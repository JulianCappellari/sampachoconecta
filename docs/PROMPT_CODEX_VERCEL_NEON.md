## Objetivo

Publicar la app **gratis y sin tarjeta** en **Vercel (plan Hobby) + Neon (Postgres, plan Free)**. Hoy la app usa SQLite con `node:sqlite` (síncrono, archivo local) y guarda las fotos en disco; Vercel no tiene disco persistente, así que hay que migrar. Al terminar tiene que quedar **todo andando y verificado** para pasar a producción, sin perder ninguna regla de negocio, de privacidad ni de concurrencia.

## Qué hay que hacer

### 1. Capa de datos a Postgres (paquete `pg`, driver TCP; sirve igual para Neon y para local)
- Instalar `pg` y `@types/pg`. Conexión por `DATABASE_URL` (en Neon, usar la cadena **pooled**). Pool chico (por ejemplo `max: 5`), `ssl` según la URL. Zona horaria de sesión UTC.
- Mantener la API `all/one/run/tx`, pero **async**. `run` devuelve `{changes, id}`: para `INSERT` en tablas con columna `id`, agregar `RETURNING id` automáticamente (las tablas sin `id` son: sessions, likes, ratings, idea_supports, pharmacy_duty, follows, notification_prefs, user_settings, poll_votes, kv, schema_migrations).
- `tx(async () => …)` debe usar `AsyncLocalStorage` para que todas las consultas de adentro usen el mismo cliente/transacción, con `BEGIN/COMMIT/ROLLBACK` y liberación del cliente.
- Una función `translate(sql)` que convierta: `?` → `$1,$2…`; `INSERT OR IGNORE INTO …` → `INSERT INTO … ON CONFLICT DO NOTHING`; `LIKE` → `ILIKE`. Revisá a mano los `INSERT OR REPLACE` (solo en el seed) y las consultas con `ON CONFLICT` ya existentes.
- Parsers de tipos de `pg`: `int8` (20) y `numeric` (1700) a `number`, para que `COUNT/SUM/AVG` no devuelvan strings.
- Compatibilidad SQL para no reescribir cientos de consultas: crear en la migración funciones SQL `datetime(text, VARIADIC text[])` (soporta `'now'`, `'now','+24 hours'`, `'-30 days'`, `'+30 days'`, `'-1 day'`, un parámetro `?` como modificador y una columna de fecha) que devuelva el texto `YYYY-MM-DD HH24:MI:SS` **en UTC**, y `julianday(text)`. Las fechas siguen siendo `TEXT` en ese formato, así las comparaciones por texto y los valores existentes funcionan igual. Reescribir a mano los pocos casos que no encajan: `strftime('%Y-%m', …)` y `date('now','-5 months','start of month')` en `src/lib/transparency.ts`, y el `COLLATE` en `src/lib/data.ts`.
- Esquema: `id INTEGER PRIMARY KEY` → identidad (`GENERATED BY DEFAULT AS IDENTITY`); `REAL` → `DOUBLE PRECISION`; `email` con `citext` (`CREATE EXTENSION IF NOT EXISTS citext`) para conservar el comportamiento `COLLATE NOCASE`; los `CHECK`, `UNIQUE`, `REFERENCES` y `ON DELETE CASCADE` se mantienen. Los triggers de la migración 3 (los reclamos y su historial **no se pueden borrar**) se reescriben con funciones `plpgsql` y `RAISE EXCEPTION` con los mismos mensajes. Verificá que siguen bloqueando `DELETE` y también `TRUNCATE` (agregá un trigger `BEFORE TRUNCATE` si corresponde) y probalo.
- Migraciones: mantener los ids 1–4 y su semántica, ahora con `schema_migrations`. Correr dentro de una transacción y con `pg_advisory_xact_lock` para evitar carreras entre instancias serverless. Las migraciones se aplican explícitamente con un script (`npm run db:migrate`) **y** de forma perezosa una sola vez por proceso al primer uso (consulta barata). Sin autoseed en producción; en desarrollo se mantiene el autoseed cuando la base está vacía.
- Ojo con las diferencias de Postgres frente a SQLite: `GROUP BY` estricto, tipos de parámetros ambiguos (agregar `::tipo` donde haga falta), expresiones booleanas que ahora devuelven `boolean` en vez de 0/1, alias entre comillas con mayúsculas, `max(a,b)`/`min(a,b)` escalares (usar `GREATEST/LEAST`), `ifnull` (usar `COALESCE`), `LIMIT/OFFSET` con parámetros. Buscalas todas con grep y revisá cada consulta.

### 2. Pasar todo el código a async
- Agregar `await` a cada llamada a `all/one/run/tx` y volver `async` a todas las funciones que las contienen, hasta las páginas, acciones y rutas. Cuidado con `.map/.forEach` con funciones async (usar `Promise.all` o `for…of` según el caso) y con las transacciones: **dentro de `tx` las consultas deben ser secuenciales** y esperarse.
- Mantener intactas las reglas: autorización del lado del servidor, `version` y `UPDATE` condicionales, `UNIQUE` para idempotencia, claves de evento únicas en notificaciones, horario de descanso, textos genéricos en avisos privados, y 404 de reclamos ajenos.
- Para no dejar promesas sin esperar, habilitá temporalmente `@typescript-eslint/no-floating-promises` y `no-misused-promises` con información de tipos, corrélos, corregí todo y dejá `npm run lint` pasando sin warnings nuevos.

### 4. Fotos: Vercel Blob con respaldo local
- Instalar `@vercel/blob`. En `saveImages`: si existe `BLOB_READ_WRITE_TOKEN`, subir a Blob (`access: "public"`, `addRandomSuffix: false`, pathname = el nombre `p|c|l|i-<uuid>.webp`, `cacheControlMaxAge` largo); si no existe (desarrollo/tests), guardar en disco como hoy. Mantener sharp (WebP, 1600 px, sin EXIF), los nombres, `NAME_RE` y los límites.
- `/api/fotos/[name]`: las `c-*` (reclamos) mantienen la autorización actual (autor o municipio) y se **sirven por proxy en el servidor** (`fetch` al blob, `Cache-Control: private, no-store`), la URL del blob nunca llega al cliente. Las demás redirigen (302) a la URL pública del blob (o se sirven con `public, max-age=31536000, immutable`).
- **Límite de Vercel:** el cuerpo de una función es de ~4,5 MB, y hoy `serverActions.bodySizeLimit` es 40 MB. Resolvelo: reducí y comprimí las fotos en el navegador antes de enviarlas (canvas → JPEG/WebP, máx. ~1600 px, objetivo < 800 KB por foto) y limitá la cantidad por envío para que quepan, mostrando un mensaje claro si no entran. Verificá el límite vigente en la documentación de Vercel. Ajustá `next.config.ts` (`output: "standalone"` solo fuera de Vercel o eliminalo si ya no hace falta, `serverExternalPackages: ["sharp"]`).
